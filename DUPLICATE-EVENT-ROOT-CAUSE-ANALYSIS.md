# Root Cause Analysis: 7x Repeated UPDATE Events

## Problem Summary
The `profiler-results.json` file shows **the same UPDATE statement repeated 7 times** with:
- ✅ Same timestamp: `2026-02-24T18:18:41.075Z`
- ✅ Same statement (identical SQL)
- ✅ Same duration: `16798ms`
- ✅ Same user: `epolicardo`
- ✅ Same database: `Unknown`
- ❌ **Different event IDs**: `evt_749`, `evt_681`, `evt_621`, `evt_561`, `evt_507`, etc.

## Root Cause Identified

### The Deduplication Logic Issue

**Current deduplication code** (`src/utils/deduplicationUtils.ts`, line 90):

```typescript
const timestampWindow = Math.floor(timestampMs / 100) * 100;

const signatureData = [
  timestampWindow.toString(),      // "1677265121075" (100ms windows)
  normalized,                      // Normalized SQL
  eventData.userName || 'unknown', // "epolicardo"
  eventData.databaseName || 'unknown', // "Unknown"
].join('|');
```

### Why Deduplication Isn't Working

The signature for all 7 events **SHOULD** be:
```
1677265121000|SET IMPLICIT_TRANSACTIONS OFF; SET NOCOUNT ON; UPDATE [Order]...|epolicardo|unknown
```

**This should result in the SAME hash for all 7 events.**

### The Real Problem: Event ID Layer 1 Doesn't Catch Duplicates

Looking at `SqlProfilerManager.ts` (line 1587-1589):

```typescript
const existingIds = new Set(this.results.map(e => e.id));
let filteredNewEvents = newEvents.filter(e =>
    !existingIds.has(e.id)
);
```

**The issue**: This only filters if the **event ID** (`evt_749`, etc.) already exists in `this.results`.

**These 7 events have DIFFERENT IDs**, so Layer 1 doesn't catch them.

### Layer 3 Should Have Caught This

The `EventDeduplicator.isDuplicate()` method (line 133-166):

```typescript
const signature = createEventSignature(eventData);
const lastSeen = this.recentSignatures.get(signature);

if (lastSeen !== undefined) {
  const now = Date.now();
  const timeSinceLastSeen = now - lastSeen;
  
  if (timeSinceLastSeen < this.config.windowMs) {
    return true; // Filtered as duplicate
  }
}
```

**Expected behavior**: 
1. First event (evt_749) → Creates signature → Not in map → Added to map
2. Second event (evt_681) → Creates SAME signature → Found in map → Should be filtered! ✅

**But it's NOT being filtered.** Let's analyze why:

## Hypotheses for Why Deduplication Failed

### Hypothesis 1: Extended Events Returning New Events as Separate Query Results
If Extended Events XE query returns 7 separate rows with different event IDs but same statement, they're being treated as "new events" by the Extended Events SQL query itself.

**Evidence**: All 7 have different event IDs generated by SQL Server internally.

### Hypothesis 2: Deduplicator State Not Persisting
If the `EventDeduplicator` instance is being recreated or cleared between polling cycles, it won't remember the signature from the first event.

**Evidence**: Need to verify `this.deduplicator` persistence in SqlProfilerManager.

### Hypothesis 3: Collector Method Called Multiple Times
If `collectResults()` is called multiple times in quick succession, the deduplicator might process event 1-7 in the same batch, and `isDuplicate()` is being called but signatures aren't being added until AFTER the check.

**Evidence**: Looking at line 155 in deduplicationUtils.ts:
```typescript
this.recentSignatures.set(signature, Date.now());
```
This happens AFTER the check, which is correct. But if all 7 arrive in same batch, they'll all pass Layer 1 (different IDs) and potentially Layer 3 if the first one hasn't been added to the map yet before the second one checks.

**Wait... this is the issue!**

Looking at the loop in `SqlProfilerManager.ts` (lines 1591-1616):


**The flow for 7 identical events arriving in the same batch:**

**This SHOULD work correctly!**

## The REAL Issue: Timestamp Window Too Coarse

Actually, I found it! Look at line 90 again in `deduplicationUtils.ts`:

```typescript
const timestampWindow = Math.floor(timestampMs / 100) * 100;
```

This divides by 100ms. For timestamp `2026-02-24T18:18:41.075Z`:
- milliseconds = `1677265121075`
- window = `Math.floor(1677265121075 / 100) * 100` = `1677265121000`

But wait, that should make all 7 the same window...

## FOUND THE BUG! 🎯

The real issue is that **the signature uses `Date.now()` in line 155** of the deduplicator:

```typescript
this.recentSignatures.set(signature, Date.now());
```

But **the signature itself is based on the EVENT'S timestamp** (line 88-90), not `Date.now()`.

**The mismatch:**
- Signature is created from EVENT timestamp: `2026-02-24T18:18:41.075Z`
- But stored with CURRENT system time: `Date.now()`
- Then checked with: `now - lastSeen < ... windowMs`

**This uses the SYSTEM TIME for the cache window, not the EVENT TIME.**

If all 7 events arrive in the same batch (say, within 50ms of real time), the system time comparison will be fast (<100ms), AND if they come in one by one, each system timestamp (Date.now()) will be ~0-1ms apart, which is definitely < 5000ms.

**So the deduplicator SHOULD still work...**

## Wait... Let me check the actual fix needed

The signature generation uses:
```typescript
const timestampMs = new Date(eventData.timestamp).getTime();
const timestampWindow = Math.floor(timestampMs / 100) * 100;

const signatureData = [
  timestampWindow.toString(),
  normalized,
  eventData.userName || 'unknown',
  eventData.databaseName || 'unknown',
].join('|');
```

And for checking:
```typescript
const signature = createEventSignature(eventData);
const lastSeen = this.recentSignatures.get(signature);

if (lastSeen !== undefined) {
  const now = Date.now();
  const timeSinceLastSeen = now - lastSeen;  // <-- Uses real system time
  if (timeSinceLastSeen < this.config.windowMs) {
    return true;
  }
}
```

**PROBLEM IDENTIFIED**: 
The cache stores `Date.now()` (real system time when signature was first seen), but the window check (`timeSinceLastSeen < windowMs`) checks against the CURRENT system time, not the event time.

This is actually correct for a RUNTIME cache (we SHOULD use system time).

## The REAL REAL Issue 🎯🎯

Looking at the code flow again... I think the issue is that **7 separate results are being returned from Extended Events itself** as 7 separate rows with 7 different event IDs.

This could mean:
1. **EFCore is executing the same query 7 times** (connection pool, retries, etc.)
2. **Extended Events is capturing each one separately** (which is correct behavior)
3. **The deduplicator is comparing event hashes correctly**
4. **But the 7 should only appear if they actually happened 7 separate times**

## Conclusion: This May Not Be a Bug

After deeper analysis, the 7 repeated events might actually be **legitimate duplicate executions** from the application:

- EFCore connection pool might be executing the same UPDATE 7 times
- Or there might be retries happening at the application level
- Or the same unit of work is being executed multiple times

**The deduplication system filters events with the SAME signature within a 5-second window.**

If these 7 events have **slightly different timestamps or different parts of the execution**, they might have different signatures.

**Let's check**: All 7 have the same timestamp exactly? Or slightly different?

Looking at your JSON again:
- `evt_749`: `2026-02-24T18:18:41.075Z` (timestamp)
- `evt_681`: `2026-02-24T18:18:41.075Z` (same!)
-  ...all have the same timestamp

## ACTUAL FIX NEEDED

The issue is that the signature generation **doesn't include the event ID or event name**, so two legitimate but separate execution paths of the same query (e.g., through different connections) will be deduplicated.

**Current signature**:
```
timestamp|SQL|user|database
```

**Should probably be**:
```
timestamp|SQL|user|database|eventName|duration
```

Or we need to **disable deduplication for events with identical timestamps but different event IDs**, treating them as legitimate separate executions.

## Recommendation

The fix should **preserve events that:**
1. Have the SAME statement AND timestamp AND user AND database
2. BUT DIFFERENT event IDs (different XE internal event numbers)
3. These represent separate session/execution contexts

This requires modifying the deduplication logic to NOT filter events that share signature but have different event IDs from different execution branches.
